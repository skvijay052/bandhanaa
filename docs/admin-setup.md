# Bandhanaa admin dashboard

## What ships

An isolated Next.js console at `/admin`, using the same Supabase project and existing domain tables. No member page is redesigned. Route groups separate `/admin/sign-in` from the protected console without changing public URLs. The root boundary disables consumer-only navigation progress and DOM enhancers on admin routes; member rendering remains otherwise identical.

The assessment in `docs/admin-architecture-assessment.md` records the source and live-schema inspection performed before implementation. The final migration uses a **private report-details table** rather than public internal-note columns, to prevent member `SELECT` queries from exposing safety notes. Profile review administrators and reasons are recorded in the audit log, not in public profile columns.

## Rollout order

1. Review this branch and test in an isolated Supabase project or restored staging database. The live project was inspected read-only; implementation tests use disposable local PostgreSQL fixtures.
2. Apply **only** `supabase/migrations/20260917174100_admin_dashboard.sql` to the existing, up-to-date Bandhanaa database, as database owner. It is a transactional, once-only additive migration. The existing standalone scripts are its prerequisites, including `razorpay-message-credit-purchases.sql` and `message-credits-required-for-all-chats.sql`. Do not rerun old base scripts over the newer live functions. The new filename was generated by the Supabase CLI; this repository's historical standalone scripts are not a complete CLI migration history, so do not blindly run `supabase db push` against production.
3. Keep `bandhanaa_private` **out of the Data API's exposed schemas**. Only the existing `public` RPC entry points need exposure. The migration grants their execution explicitly. It does not grant admins direct table-write permissions or browser service-role access.
4. Verify the existing hosting environment contains `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Keep the existing **server-only** `SUPABASE_SERVICE_ROLE_KEY` for payment operations and support email-delivery tracking. Admin reads and mutations themselves use the user's session and permission-checked RPCs, not the service key. Existing `RAZORPAY_*`, `BREVO_*` and `BANDHANAA_SUPPORT_EMAIL` configuration remains in place.
5. Deploy the application code after the migration. Contact submissions now persist in the inbox and payment-order creation checks suspension, so those routes require the new schema. The original payment verification and webhook flow is unchanged.
6. Assign the first super admin using the explicit procedure below. No account is automatically promoted.
7. Sign in at `/admin/sign-in` using that existing account. Normal member login and registration remain unchanged. Subsequent administrators are managed under **Admins & Roles**.

## First super admin: exact procedure

In Supabase Dashboard → Authentication → Users, find the **existing account you intentionally want to authorize**, confirm its email is verified, and copy its UUID. Do not choose an account by registration order or repository ownership.

Open `supabase/bootstrap-first-admin.sql` in the trusted Supabase SQL editor, replace `REPLACE_WITH_EXISTING_CONFIRMED_USER_UUID` with that UUID, review it, then run the entire script as database owner. The unedited placeholder fails safely. The transaction locks the membership table, refuses to run if any admin membership exists, verifies the user and suspension state, inserts one super-admin membership, and inserts the bootstrap audit record atomically.

Do not put this script in automated migrations, expose it over HTTP, commit credentials, or create an admin signup form. If any administrator already exists, use the authenticated role-management workflow. An administrator cannot disable or demote themselves. Administrative role changes serialize and retain an active super admin. Trusted owner-level disaster recovery is deliberately outside ordinary admin operations.

## Permission boundaries

| Role          | Pages and operations                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Super admin   | All console sections, role management, moderation, financial adjustments and support                                      |
| Moderator     | Member profiles, profile review, safety reports, connections, suspend/restore                                             |
| Support admin | Limited account details and support requests; no personal profile details, financial history, reports or private messages |
| Finance admin | Payment records and credit balances/ledger; bounded, audited adjustments                                                  |

Every privileged server page/action verifies `auth.getUser()` and active membership. Database entry points independently check `auth.uid()`, a still-existing unexpired `auth.sessions` record, confirmed email, enabled account, active membership and operation permission. Role claims supplied by the browser or editable user metadata are never used. No administrator receives private message browsing.

Admin query/action functions have fixed empty search paths. Definer implementations live in `bandhanaa_private`; narrowly granted public entry points are invoker functions. Table RLS denies direct admin-data access. Audit rows cannot be updated or deleted through the console, service role, or ordinary database operations; the owner retains ultimate database control.

## Data semantics

- **Email vs. profile review:** Existing `is_verified` remains email verification. `review_status` is a separate operations review. Completed profiles join the pending queue automatically, including existing completed profiles at migration time. No submission date existed historically, so their queue timestamp is the migration time. This is not identity-document certification; no document-submission system existed to reuse. Decisions and reasons remain in audit history.
- **Suspension:** Does not delete accounts or alter registration/email state. Restrictive RLS, write triggers, active-profile/privacy checks and the recent-visitors RPC enforce it against direct clients and existing sessions. The proxy redirects members to an account-unavailable page. Contact support and sign-out remain available. Active admin accounts must have administrative access disabled before member moderation. Publicly accessible photo files already downloaded/cached are not revoked by suspension.
- **Reports:** Preserve submitted/reviewing/resolved/dismissed and existing reason values. Internal notes/assignment live in `bandhanaa_private.admin_report_details`; prior decisions remain in audit. Concurrent stale decisions fail instead of overwriting each other. Members cannot submit a pre-resolved status.
- **Credits:** Keep the existing ledger and AFTER INSERT wallet trigger. Adjustments are limited to ±10,000 credits per operation, require a reason, lock the same wallet as message/referral/payment transactions, reject overdrafts, and create the audit record in the same transaction. A unique request ID plus a transaction lock makes retrying an adjustment idempotent; reusing its ID for another actor, amount, member or reason fails. Member-facing ledger descriptions contain no internal reason.
- **Balance snapshots:** New ledger entries record their balance after the transaction. Historical entries retain NULL; no potentially incorrect reconstruction is fabricated. Existing message/referral/payment idempotency is preserved.
- **Payments:** Read-only history using the actual Razorpay/legacy Paytm model. No provider payloads or secrets are returned. Refunds are unavailable because the application has no refund/reversal workflow. Admin never changes a payment to paid.
- **Support:** The existing Contact Us handler saves the request first, then sends the same Brevo notification. A saved request is considered received even if email delivery fails, and staff can see its delivery state. Identical submissions within five minutes share an inbox record; a database lock enforces per-account submission limits. Internal notes stay in the admin-only table. Historical email-only requests are not imported or fabricated. No admin reply-sending feature or outbound messages were added.
- **Metrics:** Total members and current queue counts are snapshots; registrations, observed activity (`last_seen_at`) and paid credits use the selected UTC period. Registration trend is a separate 7/30/90-day view. No growth percentages, fraud conclusions, unavailable metrics or mock production values are fabricated.
- **Settings:** Shows configuration-presence checks and existing code-defined business rules. It neither exposes secret values nor pretends to change settings that have no supported database model.

## Verification

The test harness requires a separately installed pinned `@electric-sql/pglite` (validated with 0.5.8); it adds no app runtime dependency. Set `PGLITE_MODULE_PATH` to its absolute `dist/index.js` path:

```sh
PGLITE_MODULE_PATH=/absolute/path/to/@electric-sql/pglite/dist/index.js node --test scripts/admin/security.test.mjs
npx tsc --noEmit
npm run build
```

The SQL tests install the actual existing application scripts and new migration unchanged, with only Supabase platform schemas emulated. They cover the role matrix, denied direct RPC/table access, session revocation, field privacy, pagination/search, credit/audit rollback, duplicate requests, overdrafts, review/safety transitions, support privacy, suspension and existing referral/payment/message behavior. PGlite uses one database connection; the tests do not substitute for a multi-session staging load test. Concurrency safety uses PostgreSQL row/advisory locks and unique indexes, not in-memory locks.

Validated on this implementation: **19 SQL/security tests passed**, including authoritative Auth email lookup, ordinary member profile edits, UTC chart reconciliation in three timezones, and the first-admin bootstrap. The production build and its TypeScript check passed with local fixture Supabase configuration. Browser checks passed for every admin section, member denial, moderator restrictions, suspend/restore, credit adjustment/reopening, report resolution, custom dates, sign-out, and the 375px mobile table/drawer layout, with no client errors. These checks did not send real email, charge a payment, or mutate hosted member data. The baseline `npm run lint` still invokes the removed `next lint` command and is not a successful verification gate for this repository.

For a disposable UI integration preview, run `scripts/admin/preview-server.mjs` with the same PGlite environment variable. It binds only `127.0.0.1:54329`, creates synthetic accounts, and exercises the real permission RPCs. In another terminal:

```sh
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54329 \
NEXT_PUBLIC_SUPABASE_ANON_KEY=local-test-publishable-key npm run dev
```

Test-only emails are `super_admin@example.test`, `moderator@example.test`, `support_admin@example.test`, `finance_admin@example.test` and `member@example.test`; the disposable test password is `local-test-only`. These identities exist only in the ephemeral local adapter. Never deploy that adapter or point production configuration at it. The application contains no demo mode or authentication bypass.

For the automated browser checks, build against the fixture URL/key first. Install Playwright and a compatible Chromium browser in a separate test environment, then run:

```sh
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54329 \
NEXT_PUBLIC_SUPABASE_ANON_KEY=local-test-publishable-key npm run build

PGLITE_MODULE_PATH=/absolute/path/to/@electric-sql/pglite/dist/index.js \
PLAYWRIGHT_MODULE_PATH=/absolute/path/to/playwright/index.mjs \
CHROMIUM_EXECUTABLE_PATH=/absolute/path/to/chromium \
node scripts/admin/browser-check.mjs
```

The browser script starts and stops its own local adapter and production Next.js server. Ports 3000 and 54329 must be available. It saves synthetic-data screenshots under `/tmp`; it never connects to the hosted Supabase project.

## Release and rollback

The code and migration should be reviewed together. The migration runs in one transaction, so a SQL error rolls back the schema change. After successful deployment and real operations, do not drop audit/ledger records or reverse the migration blindly. For an application rollback, disable admin memberships from a trusted owner environment and roll back the application deployment; keep the additive schema, operational history and security guards. A production rollout and the intentional first-admin identity are separate from creating the reviewed implementation.
